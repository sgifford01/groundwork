## 1. Purpose and career fit

A development analyst is handed a plan set in the first week and is expected to find the unit count, check the parking, measure a setback and notice that the pro forma's unit mix does not match the drawings. Nobody teaches this formally. This category teaches reading 2D drawings the way a paper set is read (sheet index → sheet → callout → detail), then turns what is on the page into the numbers a pro forma starts from: gross and rentable area, efficiency, unit mix, parking count.

It is the visual counterpart of the Excel course. It applies zoning numbers in test fits but does not teach zoning (that is `entitlements`), and it does not price construction (`construction`).

## 2. Learning objectives

1. Given a plan set, the student can use the sheet index and discipline prefixes to open the sheet that answers a stated question. (`plan-reading-set`)
2. Given a title block and revision marks, the student can state the sheet number, scale, and what changed in the latest revision. (`plan-reading-set`)
3. Given a drawing, the student can name its type (site plan, floor plan, roof plan, section, elevation, enlarged plan, wall section, detail, reflected ceiling plan) and say what question it answers. (`plan-reading-types`)
4. Given a symbol or annotation, the student can name it and locate examples on a sheet; given a callout, the student can state the sheet and drawing it refers to. (`plan-reading-symbols`)
5. Given a scale, the student can convert a paper measurement to a real length within 2% and compute an area. (`plan-reading-scale`)
6. Given a floor plan of an apartment, retail, office or mixed-use building, the student can identify its parts (core, corridor, units, storefront, lease depth, podium, drive aisle). (`plan-reading-buildings`)
7. Given a plan, the student can compute GSF, net or rentable area, efficiency, load factor, unit mix, average unit size and parking count. (`plan-reading-program`)
8. Given a plan and a stated requirement, the student can spot a problem: a missing second exit, a parking shortfall, a unit mix that does not match the stated program. (`plan-reading-program`, `plan-reading-buildings`)
9. Given a plan, the student can take off units and areas and build a mini pro forma from them in the grid. (`plan-reading-bridge`)

## 4. Key concepts, definitions and formulas

- **GSF / GBA (gross):** everything inside the exterior walls on all floors. **NRA / NSF (net rentable / net saleable):** the space that earns rent. **Efficiency** = net / gross. Typical illustrative ranges: corridor apartments 78% to 88%, office floors 82% to 90%.
- **Rentable vs. usable (office):** usable is the tenant's own space; rentable adds a share of common areas. **Load factor** = rentable / usable.
- **Dimensions** in this app's drawings are to wall centrelines and say so on the sheet. Written dimensions govern over scaled measurements.
- **Scale:** architectural = fraction of an inch per foot; engineering = feet per inch.
- **Egress basics (conceptual only):** apartments off a corridor normally need two separate exits; that is why stairs sit at opposite ends. Do not quote code distances or occupant loads.

#### Example 1: Architectural scale (`plan-ex-arch-scale`)

An architectural scale is written as inches on paper = one foot, e.g. 1/8" = 1'-0". Real feet = inches measured x feet per inch, where feet per inch is the reciprocal of the fraction (8 for 1/8", 4 for 1/4").

| Given | Name | Value |
|---|---|---:|
| Measured on paper (inches) | `paper_in` | 3.25 |
| Feet per inch at 1/8" = 1'-0" | `ft_per_in` | 8 |
| Feet per inch at 1/4" = 1'-0" | `ft_per_in_quarter` | 4 |

| Step | Name | Formula | Result |
|---|---|---|---:|
| Real length at 1/8" scale (ft) | `real_ft` | `=paper_in*ft_per_in` | 26.0 |
| Same measurement on a 1/4" drawing (ft) | `real_ft_quarter` | `=paper_in*ft_per_in_quarter` | 13.0 |

*Note.* A larger fraction is a larger-scale (more zoomed-in) drawing, so the same paper length is a shorter real distance.

#### Example 2: Engineering (civil) scale (`plan-ex-eng-scale`)

| Lot depth on paper (inches) | `depth_in` | 6.00 |
| Scale: 1" = this many feet | `scale` | 20 |

| Step | Name | Formula | Result |
|---|---|---|---:|

| Given | Name | Value |
|---|---|---:|
| Floor rentable area (SF) | `floor_rentable` | 20,000 |
| Floor usable area (SF) | `floor_usable` | 17,000 |
| Tenant usable area (SF) | `tenant_usable` | 5,000 |

| Step | Name | Formula | Result |
|---|---|---|---:|
| Load factor | `load_factor` | `=floor_rentable/floor_usable` | 1.18 |
| Tenant rentable area (SF) | `tenant_rentable` | `=tenant_usable*load_factor` | 5,882 |
| Add-on (common area) share | `add_on` | `=load_factor-1` | 17.6% |

## 5. Common misconceptions

1. Corridor, stairs and elevator count as rentable → they are common area.
2. Average unit size is the average of the unit types → it is weighted by count.
3. Efficiency = gross / net (inverted).
4. A section marker is confused with a detail callout or grid bubble → a section marker has a cut line and a direction arrow; a grid bubble sits on a centre line and holds one number or letter; a callout bubble is split, drawing number over sheet number.
5. The bottom half of a callout bubble is the detail number → the bottom is the SHEET, the top is the drawing on that sheet.
6. 1/4" scale is "smaller" than 1/8" → it is larger (more detail, less area per sheet).
7. Scaling an area by the linear factor once instead of squared.
8. Reading an engineering scale as architectural (1" = 20' read as 1/20" = 1').
9. A door swing arc is a curved wall.
10. An elevator (box with an X) is taken for a shaft/duct or a stair.
11. Plan north vs. true north ignored; "up the page" assumed to be north without checking the arrow.
12. Units are counted from tags on one floor and not multiplied by floors, or the ground floor (retail, lobby) is assumed to repeat.
13. Parking stalls counted without subtracting columns, ramps or accessible aisles where shown.
14. Property line, setback line and building line confused.
15. Rentable area and usable area treated as the same thing on an office floor.

## 8. Error hunts and spot-the-problem scenarios

1. Building program sheet that counts the corridor as rentable and averages unit sizes without weighting (grid error hunt).
2. Parking table that rounds required stalls down and omits a floor of units (grid error hunt).
3. Plan with one stair removed by a parameter (`stairs: 1`): "what is wrong with this floor?" → click the dead-end of the corridor (needs a generator parameter and an element with role `egress-problem`).
4. Parking level whose stall count is below the given requirement: compute the shortfall (measure task) and a locate task on the row that could be restriped.
5. Cover sheet project data (docreview, rendered from plan facts) where the unit count, GSF or mix disagrees with the drawings: the student must check against A-201.
6. Title block scale that disagrees with the graphic scale on the same sheet.

## 9. Case study brief and rubric

**`plan-reading-case-...` (type `timed`, level 3, about 35 minutes, pass mark 80%), with a plan set attached (section 13.4).**

*Brief.* An illustrative five-storey mixed-use building: ground-floor retail and lobby over a parking level, four apartment floors above. The student is given the plan set (cover, site plan, parking plan, ground floor, typical floor, enlarged unit, section) and a short list of given limits (FAR, required parking ratio, target unit mix). Deliverables in the grid:

1. Takeoff: units by type per floor and in total; retail area; stalls.
2. Program: GSF by floor and total, residential NRA, efficiency, average unit size, FAR used.
3. Checks: parking required vs. provided; unit mix vs. target; FAR vs. limit (each as a pass/fail formula).
4. Mini pro forma: residential and retail revenue, NOI and value from given rents and rates.

*Rubric (auto-graded).* Takeoff cells 30% (value-checked against plan facts), program formulas 35%, checks 15%, pro forma 20%. `mistakes` must cover: corridor counted as rentable, ground floor multiplied as a typical floor, unweighted average size, stalls rounded down, retail rent applied per month instead of per year.

## 11. Facts to verify at build time

- **Sheet numbering and discipline prefixes** follow widely used conventions (the U.S. National CAD Standard is the usual reference) but vary by firm. Verify the prefix list against a current public summary before writing flashcards, and phrase items as "commonly".
- **BOMA** measurement standards: name them only. Do not quote definitions or percentages from the standards.
- **Anything that sounds like a code requirement** (exit separation, travel distance, accessible stall counts, stall sizes, corridor widths): do not assert a number. Either give it as a stated requirement of the fictional project or leave it out. If the builder wants to state one real rule, it must be verified against the current official code text and the item given `verifiedAsOf` and `sourceUrl`.
- No real projects, addresses or architects.

### 13.2 Data model rules for new generators

- One file per plan set in `src/plans/`, exporting a `PlanSetDef` and registered in `PLAN_SETS`.
- Every number a question could ask for is a `fact`, named in lowercase_with_underscores (no digits), computed from the parameters, and cross-checked in `tests/plans.test.ts` against the drawn geometry (sum of room areas = gross area; counts of elements by role = count facts).
- Every drawn thing a question could ask about is its own element with a stable `role`. Roles in use: `unit, corridor, stair, elevator, lobby, core, trash, electrical, mechanical, door, window, grid-bubble, dimension, detail-callout, drawing-title, scale-bar, north-arrow, title-block, sheet-number, index-row, prefix-row, room, tub, toilet, lavatory, counter, refrigerator, range, sheet-reference, note`. Add roles as needed (e.g. `section-marker, elevation-marker, revision-cloud, revision-delta, property-line, setback-line, easement, stall, accessible-stall, drive-aisle, ramp, column, storefront, loading, retail-bay, room-tag, door-tag, window-tag`) and list them in a comment at the top of the generator.
- Labels on the drawing must not give away locate answers that the question is testing (the seed stairs are marked UP/DN, not "STAIR").
- Parameters have `limits`; every question's `variants` must lie inside them (enforced at load).

### 13.3 Viewer and type extensions (Chunk 1)

- **V1 `navigate` task kind:** `{ kind: 'navigate', from: ElementKey, correctSheet: string, distractorSheets?: string[] }`. The student is asked which sheet a callout refers to, or is asked to GO there: variant `{ kind: 'locate', ... }` already works across sheets because targets are matched in the whole set. Add a test that at least one target is NOT on the starting sheet when the prompt says "find".
- **V2 `count` and `area` answers** are `measure` tasks whose `answer` is a fact; no new kind needed. Add an optional `tool: 'area'` ruler: click three or more points to close a polygon; readout in SF (shoelace formula in `model.ts` already exists as `polygonArea`).
- **V3 Multi-select locate:** optional `pick: n` on `locate` ("click BOTH stairs"); score = correct picks minus wrong picks, over n, floored at 0 (same rule as document review).
- **V4 New marks:** revision cloud (scalloped closed path; add a `'cloud'` shape rendered as arcs), revision delta (triangle with a number), section marker (circle with a filled pointer and a cut line), elevation marker, property line (long-dash-dot-dot), setback line (dashed), hatch fill for cut walls or pavement.

### 13.4 Takeoff attachment for grid questions (Chunk 4)

Add an optional field to the sheet-graded types (`grid`, `timed`, `case`): `figure: { set, variants, sheet }` (same shape as `plan.plan`). When present, `GridQuestion` shows the `PlanViewer` above the sheet. Cells the student must read off the drawing are a new cell kind **`takeoff`**: `{ kind: 'takeoff', fact: 'unit_count', format }`. A takeoff cell is yellow like a target, accepts a typed number (not a formula requirement), and is graded by value against `set.facts[fact]` (exact, or within the cell's tolerance). Downstream formula targets are graded by the existing grid grader with the takeoff cells treated as inputs set to the CORRECT facts, so a wrong takeoff costs only its own cell (the "upstream" rule).

Implementation notes: resolve the variant with the same seed as the viewer; build the key workbook by replacing each takeoff cell with an input holding the fact; exclude takeoff cells from the hardcode check; the .xlsx round trip writes takeoff cells as plain yellow cells and notes in the instructions sheet that the plan is only visible in the app. This is an additive change to the grid types: existing items have no `figure` and must behave exactly as before (all existing tests must pass unchanged).

### 13.5 Grading API (keep UI-free, in `src/grading/category.ts`)

`planFor(item, seed) → PlanSet`; `gradeLocate(item, set, elementId | null) → { correct, message, category, picked }`; `gradeMeasure(item, set, typed) → NumericResult`; `identifyOptions(item, rng)`. Add `gradeNavigate`, `gradeLocateMulti(item, set, ids[])`, `gradeTakeoff(cell, set, typed)`.

### 13.6 Accessibility

- The SVG is focusable; arrow keys pan, + and - zoom, 0 fits (built).
- Every hotspot is a focusable `role="button"`. Before grading its label is neutral ("Drawing element 12") so that screen-reader users are not handed the answer; after grading it is the element's real name (built). Tab order should follow reading order (left to right, top to bottom): sort hit elements by position when rendering.
- Add a "List elements" toggle: a visually hidden-by-default list of the clickable elements on the sheet, each as a button labelled by neutral position ("element near grid 3 / B"), so the task is completable without a pointer.
- The Measure tool must work from the keyboard: Tab to a snap point list, Enter to place.
- Touch: one-finger drag pans, two-finger pinch zooms (track two pointers; `touch-action: none` is already set). Hotspots must be at least 24 px at fit zoom or zoom-to-target on focus.
- Colour is never the only signal: selected, right and wrong states also differ in stroke pattern or carry a ✓/✗ marker.
- Plan questions are in `DESKTOP_ONLY_TYPES`, so phone-friendly sessions skip them.
